# Developer How-To Guides (`code/howto/`)

## Overview
The `code/howto/` directory contains internal Ocean Mapping Group developer guides written by Jonathan Beaudoin and colleagues documenting how to register new multibeam/sidescan sonar `toolType` definitions in `OMG_HDCS_jversion.{c,h}` and how to manage Subversion (`svn`) repositories and merge conflicts.

---

## 1. Adding a New Sonar `toolType` (`add_new_tooltype.txt` & `add_new_tooltype_EM2040.txt`)

When adding support for a new sonar system (illustrated by the Odom ES3 as tool `#46` and Kongsberg EM2040), developers must update the following files in order:

### Step 1: Register the Tool in `code/subr/OMG_HDCS_jversion.h`
1. **Increment `NO_TOOLS`:**
   ```c
   #define NO_TOOLS 47 /* increment by 1 */
   ```
2. **Add Dimensions to `tool_defs`, `packed_tool_defs`, and `packed_tool_defs_v3`:**
   Append `{bytes_per_profile_header, max_number_of_beams, bytes_per_beam, 0}` at the end of each array (`index = NO_TOOLS - 1`). Even for variable-sized OMG-HDCS v4 files, the **maximum number of beams** (`number_beams`) in `tool_defs` must be set to the physical maximum supported by the sonar (e.g., `480` for Odom ES3, `400` or `800` for EM2040).
3. **Define the Symbolic Constant & Human-Readable Name:**
   * Add `#define ODOM_ES3 46` (or `#define EM2040 ...`).
   * Append `"ODOM ES3"` at the end of `static char *tool_names[NO_TOOLS]`.

### Step 2: Configure V4 Bitmasks in `code/subr/OMG_HDCS_jversion.c`
Inside `OMG_HDCS_initiate_V4_summary()`, add an `else if (summary->toolType == <NEW_TOOL>)` branch defining:
* **`summary->Profile_BitsDefining[0..7]`** — Bitflags selecting which ping-header fields are serialized on disk (e.g., `PROF_ui_status`, `PROF_ui_numDepths`, `PROF_ui_timeOffset`, `PROF_ui_vesselLatOffset`, `PROF_ui_vesselLongOffset`, `PROF_ui_vesselHeading`, `PROF_si_vesselHeave`, `PROF_si_vesselPitch`, `PROF_si_vesselRoll`, `PROF_si_tide`, `PROF_us_td_sound_speed`, `PROF_ss_WLZ`, `PROF_ui_watercol_offset`, etc.).
* **`summary->Beam_BitsDefining[0..7]`** — Bitflags selecting which per-beam fields are serialized on disk (e.g., `BEAM_ui_status`, `BEAM_si_observedDepth`, `BEAM_si_acrossTrack`, `BEAM_si_alongTrack`, `BEAM_ui_range`, `BEAM_ss_beam_depress_angle`, `BEAM_us_beam_heading_angle`, `BEAM_sc_reflectivity`, `BEAM_uc_Q_factor`, two-way travel time, snippet offsets, etc.).

### Step 3: Update Unravelers, `swathed`, and Recompile All Binaries
* For Kongsberg systems (`add_new_tooltype_EM2040.txt`), update `RT_unravel.c`, `RT_global.h`, `RT.c` (in `RT/` and `RTLite/`), and `swathed` (`SE/`) to recognize the new model ID and datagram conventions.
* Recompile `subr/OMG_HDCS_jversion.o` and rebuild downstream tools (`omg/`, `nav/`, `SE/`, `JV/`) so static arrays sized by `NO_TOOLS` stay synchronized.

## 2. Subversion Repository & Conflict Resolution (`subversion_howto.txt` & `resolve_subversion_conflicts.txt`)

Documents the OMG lab's Subversion (`svn+ssh://mclintock.omg.unb.ca/...`) workflows:
* Creating an `svnadmin` repository and importing initial code snapshots (`svn import`).
* Checking out working copies (`svn checkout`) and inspecting conflicts interactively during `svn update` (`(p) postpone`, `(df) diff-full`, `(e) edit`, `(r) resolved`).
* Resolving postponed conflict files (`.mine`, `.rOLD`, `.rNEW`) via:
  1. Reverting local changes (`svn revert <file> && svn update <file>`),
  2. Keeping local changes (`cp <file>.mine <file> && svn resolved <file>`), or
  3. Manually merging conflict markers (`<<<<<<< .mine ... >>>>>>> .rN`) and running `svn resolve --accept working <file>` before `svn commit`.
